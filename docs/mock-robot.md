# モック機体の使い方（実機なしで UCP を観察する）

`docs/robot-protocol.md` §8 の未確定項目のうち、**機体が無くても埋まるもの**（#7〜#10）を
埋めるための PC 側ツール。アプリから見ると「機体が居る」状態を作り、来たパケットを全部記録する。

**前提**: アプリが UCP 接続の段まで進むこと。BLE の発見や Wi-Fi 接続で止まる作りだと、
モックには何も届かない（§2 の切り分けを先に読む）。

```
uv run beni-mock-robot           # udp 0.0.0.0:9007 で待ち受ける
```

実装は [`src/beni_control/ucp.py`](../src/beni_control/ucp.py)（コーデック。PC クライアントを自作するときもこれを使う）と
[`src/beni_control/mock_robot.py`](../src/beni_control/mock_robot.py)（サーバ本体）。

## 1. これは何を埋めるか

| # | 未確定項目 | モックで埋まるか |
|---|---|---|
| 7 | ワイヤ上の `+1` フラグ（生成時の `0x12` がどう出るか） | **埋まる**（レポートが値を数える） |
| 8 | ACK ブロック末尾の u16/u32 の意味 | **埋まる可能性が高い**（`--gap-at` で sn を欠番にしてビット対応を確定） |
| 9 | Zenoh リンクフレームの形 | **一部埋まる**（magic と seq は取れる。中身の全種は機体の応答待ち） |
| 10 | keyexpr の完全形 | **一部埋まる**（ペイロード中の文字列を拾う。`put` まで進まないと出ない） |
| 1, 11, 13 | 軸の**符号**、未認証セッションの受付、速度換算 | **埋まらない**（実機が要る） |

止まる段によって取れるものが変わる。**UCP より手前（BLE 発見・Wi-Fi 接続）で止まれば何も取れない**（§2）。
UCP が繋がっても Zenoh はセッション確立に機体側の応答が要るので、上位層で止まりうる（§6）。

## 2. 準備: アプリにこの PC を `192.168.7.1` と思わせる

アプリは機体の IP を `192.168.7.1` として持っている（`docs/robot-protocol.md` §1）。
PC がそのアドレスを名乗る必要がある。スマホ側に経路を足せない（root 不要では無理）ので、
**PC がスマホのゲートウェイになる**のが手軽。

### macOS（インターネット共有で AP を立てる）

1. システム設定 → 一般 → 共有 → **インターネット共有** を Wi-Fi で有効化（共有元は有線など何でもよい）
2. ブリッジインターフェース（通常 `bridge100`）に `192.168.7.1` を足す:

   ```sh
   sudo ifconfig bridge100 alias 192.168.7.1 netmask 255.255.255.0
   ifconfig bridge100 | grep 192.168.7.1     # 確認
   ```

3. スマホをその AP に繋ぎ、アプリで機体へ接続する。
   アプリが SSID で機体を識別する場合があるので、**SSID を機体と同じ**にするのが確実
   （機体の SSID は BLE 経由の設定画面で確認できる。`docs/apk-comms.md` の GATT 参照）。

ネットワーク構成が変わったら alias は消える（`ifconfig bridge100 -alias 192.168.7.1`）。

### 動作確認

```sh
uv run beni-mock-robot            # 別端末で
# → "ucp:sync (接続確立)" が出ればアプリからのハンドシェイクが届いている
```

### つながらない場合、止まっている段は UCP より手前かもしれない

アプリは `ucp:sync` を投げるまでに何段か通る。**モックが担当できるのは 3 段目以降だけ**。

| 段 | 内容 | モックで真似しているか |
|---|---|---|
| 1 | 機体の発見（BLE の advertisement / GATT、SSID 一致） | **していない** |
| 2 | Wi-Fi 接続（資格情報は BLE 経由で機体からもらう。`docs/apk-comms.md` §3(C)） | AP を立てて SSID を合わせるのが限界 |
| 3 | **UCP 接続**（`ucp:sync`） | ここから担当 |
| 4 | Zenoh セッション → 上位層の ready 判定 | していない（§6 の限界） |

つまり `ucp:sync` が**一度も来ない**ときは、原因は Zenoh ではなく **1〜2 段目で止まっている**。
切り分け:

- `adb logcat | grep -iE "ble|gatt|scan|wifi|ucp|zenoh|connect"` を並行して見る。
  スキャンや BLE 接続で止まっていれば 1〜2 段目。
- そのスマホで**一度でも実機とペアリングしたことがある**なら、アプリは既知の機体として
  Wi-Fi 接続だけを試みることがある（その場合 SSID を機体と一致させるのが効く）。
  実機が手元に無い場合は、この経路が現実的な唯一の入口になる。
- BLE の advertisement / GATT（`0000FFF0-…`, `FFF1`〜`FFF3`）を PC 側で偽装するのは重い
  （BlueZ 等で GATT サーバを立てる作業）。まず上の 2 つを試してから。
- スマホから `192.168.7.1` に届くかも確認する（アプリの接続先はこの IP 固定）。

## 3. 走らせ方

| 目的 | コマンド |
|---|---|
| まず観察 | `uv run beni-mock-robot` |
| 全部見る（20ms で来る HB も毎回） | `uv run beni-mock-robot -v` |
| ACK ブロックのビット対応を調べる | `uv run beni-mock-robot --reply-mode hb --gap-at 5,20 -v` |
| 制御語をそのまま流し続ける（機体の HB を真似る） | `uv run beni-mock-robot --reply-mode hb --keepalive 0.02` |
| レポートを file に | `uv run beni-mock-robot --report-out cap.txt` |
| 別ポート | `uv run beni-mock-robot --port 9008` |

主なオプション:

- `--reply-mode none|ack|hb` — 返信の種類。`ack` はヘッダのみ 13B（既定）、`hb` は 39B の HB
- `--gap-at 5,20` — その sn を**送らない**。相手が欠番をどう報告するかでビット対応が決まる
- `--keepalive 0.02` — 無通信時に送る間隔。機体は 20ms で HB を出すので真似するとタイムアウトしない
- `--duration 60` — 60 秒で終了
- `-v` — 全パケットと ACK ブロックを表示

`Ctrl-C` で止めると、最後に **観察レポート**（#7〜#10 の答え合わせ）が出る。

## 4. レポートの読み方

```
--- #7  ワイヤ上の +1 フラグ
    0x10       137 個  HB(bit4) - -
    → 上の値が答え。0x10 が出ていれば『bit1 はワイヤで落ちる』が確定。
```

- **#7**: ここに出た値がそのまま答え。`0x10` なら bit1 は落ちている（doc §2.2 の推定どおり）。
  `0x12` が出たら bit1 はワイヤにも乗っている。どちらでも PC クライアントは `0x10` を送れば安全。
- **#8**: `una` と `bitmap` を、そのとき**こちらが送っていて未 cum-ack だった sn** と並べて出す。
  `--gap-at 5` を付けると sn=5 が届かないので、`relative`（= una からの相対ビット）なら
  bit0 が落ち、`absolute`（= sn そのもの）なら bit5 が落ちる。★は当てはめの自動採点。
- **#9**: magic ごとの件数と最初の seq。`0xA4`〜`0xA7` のどれが来るか、seq が連番かを見る。
- **#10**: ペイロードから拾った印字可能文字列。`device/cmd/...` が出れば keyexpr の完全形が決まる。

## 5. 併用すると確実なもの

`tcpdump` で同時に生パケットを保存しておくと、モックの解釈が怪しいときに見比べられる。

```sh
sudo tcpdump -i bridge100 -n udp port 9007 -w /tmp/beni-$(date +%s).pcap    # 実機用/AP 経由
sudo tcpdump -i lo0       -n udp port 9007 -w /tmp/beni-local.pcap         # PC 内で試すとき
```

## 6. 限界（正直なところ）

止まりうる段は 2 つある。**どちらで止まったかで取れるものが変わる**。

1. **UCP より手前**（BLE の発見・Wi-Fi 接続）— §2 参照。ここで止まると `ucp:sync` すら来ず、
   #7〜#10 は何も取れない（モックの出番が無い）。
2. **UCP は繋がるが Zenoh で止まる** — モックは UCP 層しか真似していないので、アプリは「接続した」と
   認識しても上位層（`/status/**` の受信、ready 判定）で止まりうる。この場合は **#7 / #8 と Zenoh の
   初期フレームは取れる**が、コマンドの `put` まで進まないと keyexpr（#10）は出ない。
   （止まっていないときは `seeding` の HB が来ることもある。）

さらに:

- **走行の成否は分からない**。アプリ→機体のパケットが正しく見えても、実機が未認証セッションを
  受け付けるか、その制御語で本当に前進するかは実機でしか確認できない（#1, #11, #13）。
- 観察した事実は必ず `docs/robot-protocol.md` §8 に反映して、【確定】/【推定】を更新すること。
  レポートは生データ、解釈は doc 側が正。
